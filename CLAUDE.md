# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

DSP-Effects is a growing archive of vintage-DSP-inspired audio effects, built primarily as patches for the [Polyend Endless](https://polyend.com/endless/) pedal via its `FxPatchSDK` (vendored under `sdk/`), with the same DSP code also runnable natively for offline testing and (eventually) as a DAW plugin.

Roadmap, not necessarily sequential — work can interleave across stages and devices:
- **Stage 1**: replicate the core DSP algorithms of the Lexicon PCM81 and Eventide H3000 *functionally* — right topology, right building blocks, working end to end.
- **Stage 2**: refine those implementations closer to the character of the original hardware — tone-matching, nuance, quirks.
- **Stage 3**: expand beyond those two units into new tools and an archive of other great vintage DSP devices.

Algorithms here are documented as **inspired by** the topology/character of the original hardware, never claimed as reverse-engineered or bit-exact clones — the proprietary algorithms aren't public.

`docs/references/` holds primary-source manuals/scans (e.g. the PCM81 User Guide excerpt) so specific claims in `docs/*.md` can be checked directly against them rather than taken on trust.

## Branding & versioning

The repo stays `DSP-Effects`, but the effect line itself is branded **Loom**
(the JUCE plugin's `COMPANY_NAME`/`PRODUCT_NAME`, e.g. "Loom - Lexicon
Hall") — tentative, may evolve. Versioning is repo-wide semver (`project(DSPEffects VERSION x.y.z ...)`
in the top-level `CMakeLists.txt`, pre-1.0 while the archive is young) plus
an independent per-algorithm **Stage 1/2/3** label carried in that
algorithm's `docs/*.md` — the stage label communicates DSP maturity, not
the version number. Bump the repo minor version when an algorithm reaches
Stage 1; patch for fixes/refinement within a stage.

## Architecture

Everything of DSP substance lives in `dsp/` in four tiers — Primitive → Component → Block → Graph — and is shared, unmodified, across three consumers:

- **Primitive** (`dsp/include/dsp/*.h`) — portable, header-only C++20 building blocks with **no heap allocation, no exceptions, no RTTI** (the ARM target is built with `-fno-exceptions -fno-rtti`). Current: `DelayLine` (non-owning, span-based circular buffer), `Allpass` / `ModulatedAllpass` (Schroeder diffusers), `Comb` (feedback comb / recirculating echo, continuously-settable delay length), `Crossover` (one-pole two-band splitter, low+high reconstruct the input exactly), `OnePoleLowpass` (damping/high-cut), `StereoRotate.h`'s `rotateStereoWidth` (continuously-variable mid/side stereo imaging), `Decay.h`'s `rt60ToGain` (per-line feedback gain for a target RT60), `Envelope.h`'s `LinearRamp` (one-shot ramp; used for Attack/Shape-Spread shaping and for muting output while a structural parameter like reverb Size changes), `GlideParameter` (a scalar that glides to a new target within a settable range/response, or jumps instantly beyond it — the PCM81's GldResp/GldRange), `LFO` (sine/triangle plus `nextRandomWalk()`, a smoothly-wandering random modulation source for sweep generators that are explicitly *not* sine/triangle, like the H3000's Swept Combs), `FeedbackMatrix.h`'s Householder mixing matrix for FDNs, `PitchShifter` (delay-line/grain-based real-time pitch shifter, the building block behind Eventide H3000-style effects), `PitchDetector` (autocorrelation-based real-time monophonic pitch tracker), `ReverseBuffer` (a "tape reverse" splice generator: records a settable-length segment while playing back the previous one time-reversed, ping-ponging between two fixed halves so a stable region is always available to read backward through), and `DiatonicScale.h`'s `diatonicSemitones`/`nearestScaleDegreeIndex`/`HarmonicInterval` (turning a tracked pitch plus a chosen interval into an absolute semitone shift, per-note-correct rather than a fixed transposition). The PCM81 ones map directly onto that manual's block diagrams — see `docs/lexicon-pcm81-reference.md`; the H3000 ones are grounded in `docs/eventide-h3000-notes.md`.
- **Component** (`dsp/include/dsp/*.h`) — a small reusable sub-assembly of a few Primitives, not a full effect on its own: `DiffuserChain<N>` (N Allpasses sharing one Diffusion amount), `Voice` (a `Comb` + level + pan — the repeated unit behind the PCM81's multi-voice sections), `PitchShiftVoice` (a `Delay` feeding a `PitchShifter`, one input in/one shifted output out, with a direct semitone/cents shift amount rather than pitch-tracked — the repeated unit behind the H3000's fixed-interval pitch-shift algorithms: Layered/Dual/Stereo Shift today, Multi-Shift to come), and `SweptCombVoice` (a `Comb` whose delay length wanders continuously via `LFO::nextRandomWalk()`, plus level and pan — the repeated unit behind the H3000's Swept Combs, and intended for reuse by Swept Reverb/Reverb Factory). Same directory as Primitives; the distinction is "composes other primitives" vs. "is one."
- **Block** (`dsp/include/dsp/algorithms/*.h`) — a reverb/effect core built from Primitives/Components, independent of any SDK. Exposes `prepare(sampleRate, workingBuffer)`, per-parameter setters, `process(left, right)` (whole-block) and/or `processSample(float&, float&)` (single-sample step, so a Graph can interleave it with other per-sample Components), and `reset()`. The PCM81's five reverb cores (Concert Hall, Plate, Chamber, Inverse, Infinite) share one signal path per the manual, so `ReverbCore.h` implements that shared path once (Diffusion/PreDelay/8-line Householder FDN tank/early reflections/Definition/Depth/Rvb In-Out/freeze) and each concrete core derives from it, adding only its own documented control(s) via protected hooks: `applyPreEcho()` for Plate/Chamber/Infinite's recirculating EkoDly/EkoFbk pre-echo, `effectiveDiffusion()` for dynamic diffusion shaping like Plate's Attack, `outputEnvelope()`/`shapeWetOutput()` for shaping the wet output over time (Chamber/Infinite's Shape+Spread swell via the `outputEnvelope()` scalar; Inverse's independent Low Slope/Mid Slope via overriding `shapeWetOutput()` directly, since it needs to band-split rather than just scale). `ConcertHall.h` is the reference core (no additions); `Plate.h` adds Attack + pre-echo; `Chamber.h` adds Shape+Spread + pre-echo; `Infinite.h` is Chamber + different defaults (freeze already lived on the base); `Inverse.h` replaces RT60 decay entirely with Duration+Slopes, deliberately *not* touching the recirculating feedback gain (a rising envelope needs the tank to keep sustaining so there's something to reveal - see `docs/lexicon-pcm81-inverse.md` for the bug this caught). The first Eventide H3000-family Block, `DiatonicShift.h`, is unrelated to `ReverbCore` (different device, different topology entirely): mono-sums the stereo input through one shared `Delay` and one shared `PitchDetector`, driving two independent `PitchShifter`-based Voice generators (Left, Right) from the tracked note — matching the real Algorithm 100's "the H3000 tracks your pitch and plays the correct notes" mechanism, not a fixed transposition — with each Voice's output regenerating back into the shared input for cascading harmony. See `docs/eventide-diatonic-shift.md`, including the history of why an earlier fixed-transposition version had to be rebuilt. `LayeredShift.h` (Algorithm 101) is the second H3000 Block: two `PitchShiftVoice` Components, both fed from the left input alone (per that algorithm's own manual page — not a stereo sum, unlike Diatonic Shift), each with its own Delay/cents/Feedback and no pitch tracking at all — a direct, fixed-interval shift rather than a diatonically-correct one. See `docs/eventide-layered-shift.md`. `DualShift.h` (Algorithm 102) reuses `PitchShiftVoice` unchanged for an even simpler topology: two fully independent per-channel voices with no shared input or feedback point at all ("completely separate pitch shifters" per the manual). See `docs/eventide-dual-shift.md`. `StereoShift.h` (Algorithm 103) sits between the two: independent per-channel signal paths like Dual Shift, but one shared Coarse/Fine/Delay/Feedback/Mix value drives both, matching the manual's "parameters of both channels adjust together." See `docs/eventide-stereo-shift.md`. `ReverseShift.h` (Algorithm 104) is the first Eventide Block since Diatonic Shift to need a genuinely new primitive rather than reusing `PitchShiftVoice`: mono-sums the input through two independent `ReverseBuffer -> PitchShifter` chains (own splice Length, own pitch-shift cents), since true time-reversal is mechanistically unlike the smooth continuous shifting the other Shift algorithms share. See `docs/eventide-reverse-shift.md`. `SweptCombs.h` (Algorithm 105) starts a different H3000 family entirely (no pitch shifting): six `SweptCombVoice`s, each with its own base Delay/Rate/Depth/Feedback/Pan/Level, summed into a stereo mix, with five Master controls proportionally scaling all six lines' values at once without altering the underlying per-line settings. See `docs/eventide-swept-combs.md`.
- **Graph** (`dsp/include/dsp/graphs/*.h`) — a full algorithm as the user experiences it: one Block wrapped in its class-specific front end (e.g. `ConcertHallAlgorithm.h` = the Concert Hall Block + the PCM81's 4-Voice "Reverb Shell": 4 `Voice` Components + post-delay + FX Mix/Width/Hi-Cut/Adjust; `DiatonicShiftAlgorithm.h` = the DiatonicShift Block + input level trim, no generic stereo-width control since the real algorithm's stereo image comes from two independently-harmonizing Voice generators rather than a stereo pair being rotated after the fact — see that file's doc comment; `LayeredShiftAlgorithm.h` = the LayeredShift Block + input trim on the one channel it reads, same width reasoning; `DualShiftAlgorithm.h` = the DualShift Block + independent Left/Right input trim; `StereoShiftAlgorithm.h` = the StereoShift Block + independent Left/Right input trim; `ReverseShiftAlgorithm.h` = the ReverseShift Block + input trim; `SweptCombsAlgorithm.h` = the SweptCombs Block + input trim). Patches and plugins wire up the Graph, not the bare Block.
- `patches/<device>/<algo>/` — thin Polyend `Patch` adapters (e.g. `patches/lexicon/hall/PatchImpl.cpp`, `patches/eventide/diatonic_shift/PatchImpl.cpp`, `patches/eventide/layered_shift/PatchImpl.cpp`, `patches/eventide/dual_shift/PatchImpl.cpp`, `patches/eventide/stereo_shift/PatchImpl.cpp`, `patches/eventide/reverse_shift/PatchImpl.cpp`, `patches/eventide/swept_combs/PatchImpl.cpp`) that own one Graph, map its parameters to the pedal's 3 knobs (`endless::ParamId::kParamLeft/Mid/Right`) and 2 footswitch actions (`kLeftFootSwitchPress/Hold`), and report LED color via `Patch::Color`. Each has its own tiny `Makefile` that just sets `PATCH_NAME`/`PATCH_SOURCES`/`EXTRA_INCLUDES` and includes `sdk/Patch.mk`.
- `sdk/` — vendored upstream `FxPatchSDK` (`source/Patch.h` interface, `internal/` ABI glue and linker script) plus `sdk/Patch.mk`, the shared cross-compile Makefile logic every patch includes. Treat `internal/` as upstream boilerplate; don't hand-edit it.
- `host/` — native (host-arch) CMake target `dsp_host_render` that instantiates an engine directly (no SDK involved), renders an impulse response and a test-tone burst to WAV in `--out=<dir>` (default `out/`), and prints an RT60-style decay curve. This is the fast iteration loop before touching real hardware.
- `plugin/` — JUCE-based VST3/AU/Standalone wrapper ("Loom", CMake `FetchContent`d JUCE 8.0.14) around the same engines, for testing in Ableton/Bitwig/standalone. Gated behind the `DSP_EFFECTS_BUILD_PLUGIN` CMake option so a normal build doesn't fetch JUCE. One `juce_add_plugin` target per algorithm (currently `LexiconHallPlugin`, `LexiconPlatePlugin`, `LexiconChamberPlugin`, `LexiconInfinitePlugin`, `LexiconInversePlugin`, `EventideDiatonicShiftPlugin`, `EventideLayeredShiftPlugin`, `EventideDualShiftPlugin`, `EventideStereoShiftPlugin`, `EventideReverseShiftPlugin`, `EventideSweptCombsPlugin`), each with its own `PluginProcessor` in `plugin/source/`. Every plugin's `createEditor()` returns the shared `LoomPluginEditor` (`plugin/source/LoomPluginEditor.*`): the full generic parameter list plus a "Show Architecture" button that swaps in `ArchitectureView` (`plugin/source/ArchitectureView.*`), a signal-flow diagram driven entirely by that algorithm's `dsp::schema::AlgorithmSchema` (`dsp/include/dsp/schema/`), with clickable stages (e.g. the Tank, Diffusion) drilling into a nested sub-diagram of that stage's internals — see `docs/algorithm-schema-notes.md`.

Because a `Patch`'s delay lines must live in the pedal's external working buffer (`Patch::kWorkingBufferSize` = 2,400,000 floats, `Patch::kSampleRate` = 48000) rather than internal RAM, every Block/Graph's `prepare()` takes a `std::span<float>` and carves it up itself (see `ConcertHallAlgorithm::requiredWorkingBufferSize()` / `subspan` usage, which sums its own needs plus its owned Block's `requiredWorkingBufferSize()`) — don't give primitives owned storage.

**Future direction (not yet built):** today's `plugin/` is one `juce_add_plugin` target per algorithm. The intent is to eventually also have a single, higher-level "Loom" plugin that can browse/select from the full list of algorithms across all devices and generically visualize whatever parameters the selected engine exposes, rather than requiring a separate plugin per algorithm. Likely needs each engine to expose its parameter set in some introspectable/self-describing form (name, range, current value) rather than only bespoke setters, so a generic UI can be built over any engine without per-algorithm UI code. See `docs/algorithm-schema-notes.md` for a related idea: a declarative per-algorithm schema (topology + parameters) that could drive that generic UI, auto-rendered docs/diagrams, and give AI tooling a structured artifact to reason about algorithms across devices — not yet designed; worth revisiting once a few more algorithms exist.

## Commands

Native host harness (primary day-to-day build/test loop):
```
cmake -S . -B build
cmake --build build -j
./build/host/dsp_host_render concert_hall --out=out
```
Exit code is non-zero if any rendered buffer contains a non-finite sample or a WAV fails to write; the decay curve it prints is the quickest sanity check that an engine's RT60/damping behaves.

Quick single-header smoke test without CMake, e.g. while iterating on a new `dsp/` primitive or engine:
```
g++ -std=c++20 -Wall -Wextra -I dsp/include <file>.cpp -o /tmp/smoketest && /tmp/smoketest
```

Cross-compiling an individual patch for the Endless (requires the [GNU Arm Embedded Toolchain](https://developer.arm.com/Tools%20and%20Software/GNU%20Toolchain); not available in this sandbox):
```
cd patches/lexicon/hall
make TOOLCHAIN=/usr/bin/arm-none-eabi-
```
Produces `build/<PATCH_NAME>_<timestamp>.endl` — copy that file to the Endless's USB drive to deploy. `make -n` from a patch directory is useful to sanity-check the build graph without a toolchain installed.

Plugin build (fetches JUCE 8.0.14 on first configure; needs `libx11-dev`, `libxrandr-dev`, `libxinerama-dev`, `libxcursor-dev`, `libxcomposite-dev`, `libxi-dev`, `libasound2-dev`, `libfreetype-dev` on Linux):
```
cmake -S . -B build-plugin -DDSP_EFFECTS_BUILD_PLUGIN=ON -DCMAKE_BUILD_TYPE=Release
cmake --build build-plugin -j -t LexiconHallPlugin_VST3
```
Produces a `.vst3` under `build-plugin/plugin/LexiconHallPlugin_artefacts/Release/VST3/`.
